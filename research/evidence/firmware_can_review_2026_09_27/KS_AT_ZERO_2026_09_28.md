# Native kS (param 204) at a velocity setpoint of 0 on SPARK MAX FW 26.1.5

**Question.** Bench B3 (`docs/drive_tuning_2026_09_28/tools/bench/fw26_tests.py` `b3()`) set param 204 = 0.30 V with everything else at 0. Setpoints +100 / −100 / **0** gave applied output +0.025 / −0.025 / **+0.025**, and at 0 the tracks crept forward at 51–60 RPM. Is +kS at a 0 setpoint what REV intends, a firmware bug, or a mistake in our test?

Research and code audit only. Nothing was run on the robot and no code was changed. Evidence levels are as in `FW26_CHANGES_2026_09_28.md`: A = REV spec/code, B = REV docs/staff, C = community, D = our inference. New sources are in `references/fw26_2026_09_28/`, and the README there pins them.

## Verdict: **(A) REV's intended behaviour. It is not a firmware bug, and the frames we sent were correct.** One part of our setup was wrong, which is why the bias turned into creep: **0.30 V is above the off-ground breakaway voltage**, and REV's own tuning rule for kS forbids that.

- **The firmware does what REV's own code does.** REV's closed-loop model computes `copysignf(kS, velocity_setpoint)` with no deadband and no gate, so a setpoint of +0.0 gets **+kS**. The bench matched this exactly.
- **Our frame was not at fault.** The setpoint was a true +0.0f, arbFF was 0, and P and kV were really 0. The applied output equalled kS/Vbus to 4 digits while there was 55 RPM of error.
- **What we did wrong** was to pick a kS that moves the unloaded tracks by itself. The 0.30 V value alone drove the tracks at 42–70 RPM at ±100, so the "(below breakaway)" note in `b3()` is false. REV defines kS as the largest output that does **not** move the mechanism. With a kS tuned that way, +kS at 0 is a hidden bias and causes no motion.
- **Our second assumption was WPILib's convention.** WPILib uses signum(0) = 0. REV does not claim to match it at 0.

## 1. REV documentation of kS

- **Feed-forward page** (`rev_docs_revlib_spark_closed-loop_feed-forward-control.md`, re-fetched 2026-09-28 and identical to the saved copy apart from its header) (B):
  - Line 91: "The Static Gain is used to counteract any resistance in your motor or mechanism, and is **applied in the direction of desired velocity**."
  - Line 93: "To find this value, find the smallest output that causes the mechanism to move slightly, then **decrease it slightly so that it doesn't move on it's own**, but has no resistance in that direction. … Note that kS is input in Volts."
  - Line 29 (table): kS is ✓ in all four modes, including plain Velocity Control Mode.
  - Line 8: the SPARK FF system "behave[s] **similarly** to" WPILib's feedforward classes and "is designed to drop-in to many of the use cases". It says "similarly", not "identically".
- **REVLib 2026 Javadoc, `FeedForwardConfig.kS`** (`rev_revlib_javadoc_2026_FeedForwardConfig.txt`) (A): "Set the kS Static Gain of the controller. This will set the value for closed loop slot 0." and "kS - The kS gain in Volts". **It says nothing about sign, zero setpoint or at-setpoint behaviour.**
- **Zero setpoint:** no REV page says what happens at exactly 0. "Direction of desired velocity" is undefined at 0. **The documentation is silent on this.**

## 2. REVLib's closed-loop code (REV code; "translated directly from the Spark firmware", `SparkSim.java:190`)

Source: `rev_revlib_driver_2026.0.5_sim_disassembly.txt` (A-sim). The equations are decoded in the references README.

- **`CANSpark.cpp:1233`**: `sgain = copysignf(kS, state.velocity)` (disassembly line 38: `call copysignf@plt`). The function is `copysignf`, not `signum` and not a `>= 0` test.
  - copysignf(kS, +0.0) = **+kS**.
  - copysignf(kS, −0.0) = −kS.
  - There is no deadband.
- **`CANSparkDriver.cpp:2286-2289`**: in velocity mode the state passed is {pos 0, **vel = setpoint**, acc 0}, with signals {s=1, v=1, a=0}. The sign therefore comes from the **setpoint**. It does not come from measured velocity or from error.
- **Gating:** the s-signal is 1 unconditionally in velocity mode. Nothing gates it by velocity, error or setpoint.
- **Param 97** is "Allowed Closed Loop Error 0: PID Slot 0: Range of error from the target value." (`rev_revlib_driver_2026.0.5_param_defaults_gdb.txt:100`, default 0.0).
  - In the sim (`CANSpark.cpp:1316-1319`), `|error| ≤ allowedErr` returns **clamp(ff)**: P/I/D are dropped and the **feedforward, including kS, is still applied**.
  - So 97 does not gate kS. It would even remove the P term that resists creep.
- The bench matches all of this: the sign followed the setpoint (−kS at −100 starting from rest, so the sign is not taken from measured speed), and the sign did not flip when the error went negative (setpoint 0, speed +55), so it is not taken from error.

## 3. Reference conventions

- **WPILib** `SimpleMotorFeedforward` v2026.2.1 (`wpilib_v2026.2.1_SimpleMotorFeedforward.java:164,190`) (A for WPILib): `ks * Math.signum(velocity) + kv * velocity …`. **signum(0) = 0**, so WPILib gives no kS at a zero setpoint. REV says only "similarly" (§1), and its code uses copysign.
- **CTRE Phoenix 6** `StaticFeedforwardSignValue` (`ctre_phoenix6_StaticFeedforwardSignValue.txt`) (A for CTRE):
  - `UseVelocitySign`: "works well with velocity closed loop".
  - `UseClosedLoopSign`: "We recommend the minimal amount of kS, otherwise the motor output may dither when closed loop error is near zero."
  - Vendors treat the zero case as the user's problem and ask for a kS small enough not to move the mechanism.

## 4. Community evidence (C)

We searched Chief Delphi, REV-Software-Binaries issues (GitHub search for "kS": 0 hits) and web search for "kS" together with creep/zero setpoint/spins at 0 on FW 26. **No report, bug or REV statement about kS at a zero setpoint was found.**

- The only related thread is "Spark MAX error when setting kS" (param 204 is invalid before FW 26; already in FW26_CHANGES §6).
- The common FRC practice for stopping is `stopMotor()` / duty 0 / `setVoltage(0)` rather than a velocity-0 reference. For example, CD "Spark Max PID Velocity control…" recommends duty cycle to coast down, because P brakes at a 0 setpoint. That practice also sidesteps kS at 0 (C/D).
- The absence of reports is consistent with most teams using kS at or below breakaway, as REV instructs.

## 5. Does REV intend velocity 0 to be held by the PID, and can kS be gated?

- **Hold at 0:** REV intends velocity 0 to be a closed-loop setpoint like any other: FF + PID, with kS ≤ breakaway so that the bias causes no motion (D, from §1 line 93 + §2).
- **No kS gate exists on FW 26.1.x.**
  - There is no "kS only when not at setpoint" option and no feedforward velocity threshold. The 2026.0.5 parameter table has no such parameter; the only FF parameters are 204–208 + 5·slot and 16.
  - 97 (PID tolerance) keeps FF on (§2).
  - The sm-26.x release notes mention no kS change.
- **Ways to get no kS at 0:** switch to duty 0 (idle mode), or put kS in the ARBITRARY_FEEDFORWARD field with your own sign logic and keep 204 = 0.

**Bottom line.** The user is right that the controller behaves as REV designed. Our frames were correct. Our mistakes were a kS above breakaway and the assumption of WPILib's zero convention. The finding "native kS applies +kS at a setpoint of exactly 0" is still **true and REV-intended**. With a correctly sized kS it is a harmless forward bias, not creep.

## 7. Recommended use of native kS in a velocity drivetrain on FW 26

1. **Keep the current design (preferred).** Param 204 = 0 (CHK enforces it), with kS in the Teensy arbFF with its 1 RPM deadband. This is the WPILib signum convention, gives exactly 0 at a 0 setpoint, and allows per-side kS_left/kS_right.
2. **If native 204 is used instead:**
   - (a) Size kS **below the loaded breakaway** (REV rule). Measure it on the ground per side, and recheck off the ground, where breakaway is lower: an on-ground value can creep on the stand.
   - (b) Never hold a stop with velocity 0. Stop with duty 0 / idle Brake, as `S` and the watchdog already do (`STOP_TO_IDLE`).
   - (c) Accept that a track commanded exactly 0 while the other moves (a pivot about one track) gets a +kS forward bias that P/I must hold off.
   - (d) Keep 97 = 0, because a non-zero tolerance drops P/I but keeps kS.
   - (e) Never combine 204 with arbFF kS: they add (B5).

## 8. Decisive bench tests for the remaining doubt (tracks off the ground, RAM only, actuator_node stopped)

- **D1: REV-intended use is harmless.**
  - Find the off-ground breakaway with 204 alone at L100: step 0.05 V up until motion starts, then set 204 ≈ 80 % of it.
  - Then run L100 / L-100 / L0 as in B3.
  - Expect applied ±kS/Vbus and +kS/Vbus at L0, with **0 RPM** in all three. If it creeps at L0 while not moving at L100, the firmware is doing something beyond copysign.
- **D2: deadband probe.** With 204 = 0.30 V, command L0.5, L-0.5, L0.01 and L-0.01.
  - Expect the sign to follow the setpoint down to ±0.01, which means there is no firmware deadband.
  - Any 0 applied output means a deadband exists and REV code ≠ firmware.
- **D3: copysign or `>= 0`** (academic, because v2d only ever sends +0.0). This needs a raw frame with setpoint bytes `00 00 00 80` (−0.0f), which requires a test-only Teensy build or a USB-CAN adapter.
  - −kS means copysign, as in REV's code.
  - +kS means a `>= 0` test.
- **D4: at-setpoint gating** (optional). Run B3 L0 with param 97 = 100 RPM. Expect +kS unchanged, because the tolerance keeps the FF.
