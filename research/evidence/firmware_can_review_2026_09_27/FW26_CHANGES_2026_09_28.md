# SPARK MAX firmware 25.0.4 → 26.1.5: what changes for our Teensy CAN bridge (2026-09-28)

Scope: 2 × SPARK MAX (NEO, hall sensor), now on **FW 26.1.5**, driven by Teensy firmware v2c (`firmware/teensy_diff_drive_v2/`), no roboRIO. This is research only: no code was changed and nothing was run on the robot.

**Already observed on 26.1.5:** FV reports 26.1.5; STATUS_0 model = 2; every parameter ID reads back; param 204 (kS) writes OK; param 16 still holds 0.000197; idleMode on L is 1.

**Reference tags.** Files in `references/` are cited by name. New files are in `references/fw26_2026_09_28/`; its README pins each URL, version and sha256.
- **JSON**: `rev_2026_spark_frames_2.1.0.json`. This is still the newest REV-Specs version (repo HEAD 1e90305, 2026-01-02).
- **HDR**: `rev_2026_revlib_driver_2026.0.5_CANSparkFrames.h`.
- **NOTES**: `fw26_…/rev_release_notes_sm26_revlib2026_rhc_2026_09_28.md` (GitHub release bodies).
- **SIM**: REVLib 2026.0.5 simulation code.
  - Java part: `fw26_…/rev_revlib_java_2026.0.5_SparkSim.java`.
  - Native part: disassembled with DWARF line info in `fw26_…/rev_revlib_driver_2026.0.5_sim_disassembly.txt`, cited as `CANSpark.cpp:<line>`.
  - REV says the simulation's algorithms are "translated directly from the Spark firmware" (SparkSim.java:190). It is **REV code, but not the firmware**, and it has open bugs (issue #29). Every SIM-only answer is marked **(SIM)** and has a bench test in §9.
- **PDEF**: `fw26_…/rev_revlib_driver_2026.0.5_param_defaults_gdb.txt`, REVLib's built-in parameter table (ID, type, default, description).
- **Evidence levels**: A = REV spec or REV code; B = REV docs or REV staff; C = community; D = our own inference.

Newest versions (checked 2026-09-28): sm-26.1.5 (2026-03-12) is the newest SPARK MAX firmware and REVLib 2026.0.5 the newest 2026 library. 2027.0.0-alpha-7 exists, but it targets FW 27 / Systemcore. **No spec or header newer than 2.1.0 / 2026.0.5 applies to FW 26.1.x.**

## 1. Feedforward on FW 26 (kS 204, kV 16, kA 205, kG 206, kCos 207, kCosRatio 208)

| Question | Answer | Source (level) |
|---|---|---|
| Units | kS, kG: V. **kV: V per RPM** (per velocity-conversion unit). kA: V per (RPM/s). kCos: V (units page says "V per rotation"; the FF page says V). kCosRatio: ratio from sensor units to mechanism rotations. | `rev_2026_closed_loop_units.md` "Default Units"; `fw26_…/rev_docs_…feed-forward-control.md` quick-reference table (B). Parameter IDs: `rev_2026_revlib_java_2026.0.5_SparkParameters.java:51,191-195` (A) |
| Param 16 after the update | It is kV in volts. **REVLib does not rescale it**: the deprecated `velocityFF(ff)` writes the raw value into `kV_0` (`ClosedLoopConfig.java` 2026.0.5, `velocityFF(double, slot)` → `putParameter(kV_0 …, ff)`). | Conversion to output | **(SIM)** `ff_V = s·copysign(kS, v_ref) + v·kV·v_ref + a·kA·a_ref + g·kG + cos·kCos·cos(…)`. Then **duty = ff_V / ref**, where ref = **measured bus voltage** if voltage compensation is off (param 74 = 0), or param 75 (nominal V) if it is on. The duty is added to P+I+D, and the sum is clamped to [outputMin(19), outputMax(20)]. | `CANSpark.cpp:1232-1273` (CalculateFeedforward), `:1294-1341` (CalculatePID) |
| With voltage compensation on | **(SIM)** Everything is then multiplied by nominal/Vbus (`SparkSim.java:338-348`), so the feedforward is still ff_V/Vbus. **Voltage compensation changes only the P/I/D terms (duty), not kS/kV.** kV in volts already self-compensates for bus sag. | SIM (A-sim) |
| kS sign | **(SIM)** In **velocity mode** kS takes the sign of the **velocity setpoint**: the state passed is {pos 0, vel = setpoint, acc 0} (`CANSparkDriver.cpp:2286-2289`). It does not use measured velocity or error. In **position mode** the sign comes from the error (`:2295-2298`). The docs agree: "applied in the direction of desired velocity" (feed-forward page line 91, B). | SIM + B |
| kS deadband | **None in SIM.** `copysignf(kS, +0.0)` = +kS, so a velocity setpoint of exactly 0 gets **+kS** (a −0.0 setpoint gets −kS). Whether the firmware has a deadband is **not confirmed** (bench B3). Our v2c arbFF path has a 1 RPM deadband (`ino:487,508-513`). | SIM (A-sim); D |
| kA in plain velocity mode | **No.** Velocity mode sets the signals {s=1, v=1, a=0} (`CANSparkDriver.cpp:2289`). The docs table marks kA ✓ only for MAXMotion position and MAXMotion velocity. MAXMotion velocity uses {s,v,a} = 1 with the profile's acceleration (`CANSpark.cpp:1546`). | SIM + B (feed-forward page line 29) |
| kG / kCos / kCosRatio | Position and MAXMotion-position only (docs table; SIM signals g=1, cos=1 in position mode). Not relevant to us. kCos has a known **sim-only** bug (#29). | B; `fw26_…/github_rsb_issue29.md` |
| ARBITRARY_FEEDFORWARD vs kS/kV | **(SIM) Additive.** The closed-loop output (P+I+D+configured FF, clamped) is computed first. The frame field is int16 × 0.0009765923 (±32 V) at bits 32–47 (JSON:716 VELOCITY_SETPOINT). **Writing param 204 while also sending v2c's arbFF kS applies kS twice.** | SIM; JSON (A) |
| PID tolerance (param 97, new in 26.1.0) | **(SIM)** If `|error| ≤ allowedClosedLoopError(97+4·slot)`, the output is **feedforward only**: P/I/D are dropped and the I accumulator is held. Default 0 (PDEF). Keep it at 0 unless used on purpose. | `CANSpark.cpp:1316-1320`; notes sm-26.1.0 "Adds ability to set a PID tolerance outside MAXMotion"; issue #16 (REV member) |

**Not confirmed without a bench test:** that the firmware divides by *measured* bus voltage (as SIM does) rather than a fixed 12 V; the zero-setpoint kS behaviour; that kA is ignored in plain velocity mode on real hardware.

## 2. Frames and signals on FW 26

- **"Removes Legacy Status Frame 0" (sm-26.1.4)** is class 6 index 0 (arb 0x2051800, `LEGACY_STATUS_0`, JSON:6, "versionDeprecated 25.0.0"). **Our STATUS_0 is class 46 index 0 (0x205B800, JSON STATUS_0) and is not affected.** It still carries SPARK_MODEL (bits 54–57; 2 = MAX per sm-26.1.0) and PRIMARY_HEARTBEAT_LOCK (bit 53).
- **New or changed status frames on FW 26** (sm-26.1.0 "new status frame … closed loop control status" and "… MAXMotion status"; sm-26.1.2 "Fixes issue in initializing status 8"). Layouts are from JSON:633-700, with frame IDs and lengths matching HDR:371-373 and :701-703. All are little-endian and off by default.

| Frame | Arb ID (dev 0) | Default period | Period param / force-enable param | Signals (bit pos, length, type) |
|---|---|---|---|---|
| STATUS_7 | 0x205B9C0 | 20 ms | 165 / 193 | I_ACCUMULATION 0,32 float; RESERVED 32,32 |
| STATUS_8 | 0x205BA00 | 20 ms (JSON); PDEF says param 199 default 10 | 199 / 200 | SETPOINT 0,32 float (RPM in velocity mode); IS_AT_SETPOINT 32,1 bool; SELECTED_PID_SLOT 33,4 uint; RESERVED 37,27 |
| STATUS_9 (new, versionImplemented 26.0.0) | 0x205BA40 | 100 ms | 224 / 225 | MAXMOTION_POSITION_SETPOINT 0,32 float; MAXMOTION_VELOCITY_SETPOINT 32,32 float |

  STATUS_3–6 are analog, alternate, and duty-cycle encoder frames; we don't use them.
- **SET_STATUSES_ENABLED bit mapping is confirmed as bit n = STATUS_n.** REVLib builds the bitfield as `|= 1 << statusIndex`, sends **mask 0xFFFF** and DLC 4, and waits for STATUS_0 first (`SparkFrameManager.cpp:80-134`, disassembly file) (A). To add STATUS_7/8, our mask/enable becomes **0x0187**.
- **sm-26.1.3 "enabling an enabled periodic frame would reset the time to send out the frame".**
  - On FW 25.0.4 our 1 s SET_STATUSES_ENABLED re-send therefore restarted the STATUS_2 timer once a second. Each restart stretches one interval to up to 2 × 20 ms.
  - This matches the bench S1 result "STATUS_2 20.2 ms (about 1 % at 40 ms)" (`docs/…/BENCH_SCOPES_2026_09_28.md` S1) (D).
  - On 26.1.5 the fix is included, so the keepalive becomes harmless. Verify with B7.
- **PID tolerance** is param 97 (see §1). IS_AT_SETPOINT in STATUS_8 reflects it (SIM `CANSpark.cpp:1318` sets the at-setpoint flag).
- **Newer spec or REVLib:** none for FW 26 (see header). The 2027-alpha-7 headers in `references/` are for FW 27 and remove 112/113/136/137.

## 3. Hall velocity filter (136 / 137)

- **Still present and typed the same in REVLib 2026.0.5.** 136 `kUvwSensorSampleRate` is FLOAT, **seconds**: `uvwMeasurementPeriod(ms)` writes `ms/1000` with the comment "Convert from period (ms) to native units (seconds)", `rev_2026_revlib_java_2026.0.5_EncoderConfig.java:182-186`. 137 is UINT32 index 0–3 = 1/2/4/8 samples (A).
- **The default is 0x3D000000 = 0.03125 s** (PDEF id 136; also `rev_2025_spark_parameters_v0.1.2.md:203`) (A). No source uses 0.1 s or ms/100 units. **The "raw 0.3125" in BENCH_2026_09_28.md:39 does not match any REV default.** It is most likely a transcription or formatting slip (0.03125 → 0.3125) and should be re-read as raw hex (B8) before anything writes 136.
- **Honoured:** on FW 25.0.4, 137 = 3→1 cut the reported-speed lag from 140 to 46 ms (`BENCH_2026_09_28_part2.md` §2) (D). No FW 26 note changes the hall filter. REVLib 2027-alpha-7 "Removes hall sensor velocity averaging configurations in favor of new firmware filtering system", which implies FW 27, not 26.1.x (NOTES). **Not confirmed on 26.1.5** until B8.
- The default velocity measurement is unchanged per sources. The quadrature defaults (70 = 64, 71 = 200 × 500 µs) don't affect the hall sensor. The sim uses a fixed 2-tap × 16 ms average (`SparkSim.java:52`), which is not tied to 136/137, so the sim tells us nothing here.

## 4. MAXMotion velocity on FW 26

- **Setpoint frame:** MAXMOTION_VELOCITY_SETPOINT, class 0 index 9, arb 0x2050240 | dev, DLC 8. Its layout is identical to VELOCITY_SETPOINT: float setpoint (RPM), arbFF int16 bits 32–47, slot bits 48–49, FF-units bit 50 (JSON:977) (A).
- **Parameters for slot s** (SparkParameters.java:153-172; PDEF defaults all 0):

| Param | ID | Notes |
|---|---|---|
| MaxAccel | 167 + 5s | RPM/s. **Honoured** in velocity mode |
| CruiseVelocity | 166 + 5s | **Not honoured** in MAXMotion *velocity* mode. The docs say "does not honor it … clamping … must be done before" (getting-started page line 173) (B) |
| MaxJerk | 168 + 5s | PDEF: "[Not implemented yet]" |
| AllowedProfileError | 169 + 5s | |
| PositionMode | 170 + 5s | Position control only |

- **Feedforward:** kS + kV·v_profile + kA·a_profile, all three enabled (SIM `CANSpark.cpp:1546`; docs "you should be able to get decent performance with only kV/kA and no PID"). The internal profile velocity is visible in STATUS_9. sm-26.1.0 "Reworks MAXMotion for smoother and more consistent motions".
- **Could it replace the Teensy/host slew?** Partly (D).
  - There is **one maxAccel per slot, used for both accelerating and decelerating**. Our actuator is asymmetric: 0.3 m/s² accel, 1.3 m/s² decel, which is 903 and 3912 RPM/s at 0.01994 m/rev.
  - To keep the asymmetry, the Teensy would pick slot 0 (accel) or slot 1 (decel) per frame. Each slot needs its own full PID+FF copy (13–20 + 8·s, 204–208 + 5·s, 97/96 + 4·s).
  - What the profile does when the target is re-sent every 20 ms with a changing value is **not documented**. It needs B9 before we rely on it.
  - The stop-to-idle path (duty 0) stays as it is.

## 5. Heartbeat, enable, persist, reads, RHC2 coexistence

- **Universal and secondary heartbeat:** no sm-26.x note mentions any heartbeat change (NOTES) (A).
  - The spec still defines SECONDARY_HEARTBEAT (class 11 index 2) and the STATUS_0 heartbeat lock bit 53, which means "ignore the Secondary Heartbeat until it is power cycled" (JSON).
  - The only related fix is sm-26.1.0 "Fixes bug that can prevent force enable parameters from resetting correctly" (186–193, 200, 225).
  - Our big-endian all-zero "disabled" frame was proven on 25.0.4. **Re-run HB0 on 26.1.5** (B10) to confirm it still disables.
- **Persist:** no FW 26 change is documented. REVLib 2026.0.5 still has `kCannotPersistParametersWhileEnabled = 26` (`rev_2026_revlib_cpp_2026.0.5_REVLibError.h`), and a REV engineer states persist "must only be done when disabled" (`wpilib_2024_2025beta_issue69_persist_error.md`). **Keep the disabled-heartbeat BURN sequence.**
- **Parameter reads:** they worked on 25.0.4 (bench) and have been observed working on 26.1.5 (the "all IDs read back" fact). The spec note that reads are unsupported on a MAX is obsolete.
- **REV Hardware Client:**
  - FW ≥ 26.0.0-prerelease.2 bridges USB to CAN with **SLCan**, and **only RHC2 works over USB** (sm-26.1.0 note). RHC2 needs 26.x (RHC2 overview "REV Device Requirements"). RHC1 is end-of-life (rhc-1.7.7).
  - RHC2 1.0.3 "Adds warning when trying to run a motor with the roboRIO present on the bus".
  - RHC2 1.1.0 "Improves SPARK setpoint handling to minimize interfering with a connected robot's setpoint commands".
  - The run-motor guide says RHC will not run a motor if a roboRIO was connected, and to power-cycle the SPARK. That is the heartbeat lock.
  - **Conclusion (D):** with our Teensy sending the universal heartbeat, the SPARKs lock, so RHC2 should be able to read and write parameters and show telemetry but *not* run motors. **That RHC2 can connect cleanly while the Teensy runs is not confirmed.**
    - REVLib-style hosts send SET_STATUSES_ENABLED with mask 0xFFFF, which could switch off our STATUS_2 until our 1 s re-send restores it.
    - Whether RHC2 treats a Teensy heartbeat as "roboRIO present" is unknown.
    - The project CLAUDE.md records that the Teensy and RHC "fight for the bus".
    - Test with B11. Until then, do RHC2 work with the Teensy's heartbeat stopped.

## 7. Idle mode

- **No FW 26 change to idle-mode behaviour or defaults is documented** (NOTES, all sm-26.x).
- REVLib 2026.0.5's table default is 0 = Coast (PDEF id 6). Legacy docs: "kIdleMode … default IDLE_COAST … persists through a normal firmware update" (`fw26_…/rev_docs_brushless_spark-max_parameters.md`).
- Our flash held Coast on both (part2 §6). **L = 1 after the update has no documented cause** (not confirmed). Possibly RHC2 was used during the update, or the update reset some parameters. REV recommends a factory reset + persist after the first update to 25+ (sparkmax-25.0.0 note), which was never done.
- **Action:** read 6 on both sides, write the chosen value explicitly (UINT32) on both, BURN, power-cycle, and read back (B12).
- Behaviour in our stop path is unchanged: duty 0 → idle mode. This was part2 §4's finding on FW 25; re-check the stop test once (B12).

## 10. Summary answers
1. **FF:** 16 = kV in V/RPM (not rescaled; ours is 12× weak). kS/kG in V, kA in V/(RPM/s). SIM: FF volts / measured Vbus (or / nominal when compensation is on, which nets to the same), added to PID before the output clamp. kS sign = velocity-setpoint sign, no deadband (+kS at 0.0). kA only in MAXMotion. arbFF is added on top (volts/Vbus or duty).
2. **Frames:** our STATUS_0 is the class-46 one (legacy class 6 removed). Add STATUS_7 (float I-accum) and STATUS_8 (float setpoint, bit 32 at-setpoint, bits 33–36 slot); SSE bit n = STATUS_n. 26.1.3 fixes the keepalive jitter. No spec or header newer than 2.1.0 / 2026.0.5.
3. **Hall:** 136 is float seconds, default 0.03125 (0x3D000000). "0.3125" is most likely a misread. 137 is an index; both are still present in FW 26. Removal is a FW 27 / REVLib 2027 change.
4. **MAXMotion velocity:** class 0 index 9, same layout; 167 accel (RPM/s), cruise not honoured, jerk not implemented; uses kS + kV + kA. One accel per slot, so asymmetric decel needs slot switching. Retargeting behaviour untested.
5. **Heartbeat/persist/read:** no FW 26 changes documented; keep the disabled-heartbeat BURN. Reads work. USB is SLCan and RHC2-only; the heartbeat lock blocks RHC2 "run"; coexistence is not confirmed.
6. **Known issues:** only fixed ones (status-8 init, frame-timer reset); current-mode bug not relevant; sim bugs (#29). No 26.1.x velocity-control bug found.
7. **Idle:** no FW 26 change or default change documented (default Coast). L = 1 is unexplained; write it explicitly, BURN, and verify.
