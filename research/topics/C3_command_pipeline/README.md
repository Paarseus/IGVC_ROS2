# C3 — Command pipeline

| | |
|---|---|
| **Question** | How should the chain from navigation controller to motors be layered, arbitrated, limited, timed out and stopped, and what do control theory, machine-safety standards, real-time systems research and reference robot stacks say about each link? |

## Summary
- Layered ("cascade") control only works when each lower loop is much faster than the loop above it: a separation of 4 (minimum) to 10 (preferable) in closed-loop time constant; at about 3 or less the layers interact ("fight") and performance degrades even with a perfect model. Saturation in an inner loop winds up the integrator of the outer loop unless anti-windup is applied there. PX4's rover and multicopter controllers use an inner rate loop at the bottom of the chain, designed as part of the cascade: it is tuned first and the outer loops are built on it. [C3-S03, section 2.5, p. 9; section 3.9, p. 20; C3-S01, section 11.6, pp. 341–342; C3-S41, `index.md`, `rate_tuning.md`; C3-S40, "Multicopter Control Architecture"]
- Reference ROS 2 stacks put a clear order on the chain — controller → velocity smoother → collision monitor → base controller — with each stage having its own job: the controller plans dynamically feasible motion, the smoother limits velocity/acceleration and adds a deadband and timeout, the collision monitor is a last "emergency-stop-level" filter, and the base controller applies its own limiter and command timeout. [C3-S19, "Design"; C3-S21, "Design"; C3-S22, `cmd_vel_in_topic`/`cmd_vel_out_topic`; C3-S27, `cmd_vel_timeout`]
- Arbitration in ROS 2 is usually a priority multiplexer: twist_mux forwards the highest-priority input that has not timed out and is not masked by a lock; it only forwards on message arrival and never publishes a zero itself, so stopping after a timeout relies on the downstream timeouts. [C3-S24, `topic_handle.hpp` lines 109–113, 189–206, 285–287; `twist_mux.cpp` lines 140–143, 183–224]
- Emergency stop is a "complementary protective measure" that should take effect when guards and protective devices have failed; it is implemented as stop category 0 (remove power, e.g. STO) or category 1 (controlled deceleration, then remove power). In the ISO 13849 Category 2 designated architecture, the test equipment that evaluates diagnostics should normally be engineered outside the functional channel (e.g. a separate watchdog), and test equipment that is software-only and drives the test-equipment output (OTE) directly by a software-generated de-energizing signal is not acceptable. [C3-S09, pp. 29–30, 34, 52; C3-S36, p. 6]
- Stale-command handling is layered: Nav2's smoother zeroes its target after `velocity_timeout` (default 1.0 s) and decelerates at its limits; diff_drive_controller zeroes after `cmd_vel_timeout` (default 0.5 s) measured on the message stamp; Clearpath and twist_mux defaults use 0.5 s per source; ROS 2 QoS deadline and liveliness can report a silent publisher at the middleware layer. [C3-S18, `velocity_timeout`; C3-S20, lines 257–264; C3-S28, lines 124–133 and `parameters.yaml` lines 99–103; C3-S29; C3-S33, "QoS policies"; C3-S34, "Deadline", "Liveliness"]
- Latency adds phase lag ωτ and limits the achievable loop bandwidth. In ROS 2, the default executor's polling rules delay and reorder callbacks, and in one multi-node study the DDS layer and the delay between message notification and retrieval were the largest latency contributors. In a Linux real-time communication test, a PREEMPT_RT kernel cut worst-case scheduling latency from 13197 µs to 88–110 µs. ros2_tracing, a low-overhead tracing tool (mean added end-to-end latency 0.0033 ms per message), is used to measure it. [C3-S01, section 9.4, p. 283; C3-S07, section 3, p. 6:6; C3-S12, section 5; C3-S14, section IV; C3-S08, section VI]

## Findings

### 1. Pipeline architecture and layering (general)
- Nav2 is a set of task servers (planner, controller, recovery) orchestrated by a behavior tree; the servers are ROS 2 managed ("lifecycle") nodes with defined state transitions, stepped through inactive → active → finalized by a lifecycle manager. [C3-S04, pp. 2–3 and section IV-F "Utilities", p. 5]
- For the MPPI model-predictive controller described in the Nav2 survey, the first control of the optimal trajectory is "sent to the robot base controller to track" and the optimisation is repeated at the next time step; the controller therefore relies on a lower layer to realise the velocity. [C3-S05, section IV, p. 8]
- The velocity smoother is designed to take the command from Nav2's controller server and smooth it "for use on robot hardware controllers" (input `cmd_vel`, output `cmd_vel_smoothed`). [C3-S19, "Design"]
- The Collision Monitor is designed to "operate below Nav2 as an independent safety node" acting as a filter on the controller's `cmd_vel`; its default input is `cmd_vel_smoothed` and default output `cmd_vel`, i.e. it sits after the smoother and before the base. [C3-S21, "Design"; C3-S22, `cmd_vel_in_topic`, `cmd_vel_out_topic` and example YAML]
- ros_control separates a hardware abstraction layer (typed state/command interfaces for actuators and sensors) from a controller manager that manages controller lifecycle and resource conflicts; it was created because ROS lacked a real-time-safe communication layer. [C3-S06, pp. 1–2]
- The ros2_control controller manager runs one loop at `update_rate` that "reads states from hardware, updates controller and writes commands to hardware". [C3-S26, `update_rate`]
- Autoware's `vehicle_cmd_gate` receives commands from the planning module, an external (remote) controller and the emergency handler, selects one, and applies a final guard filter before the vehicle interface (car domain). [C3-S32, "Purpose", "Main Functionality"]
- Mars Exploration Rovers used three command layers: low-level motor commands, "directed" driving primitives (arcs, straight lines, turns in place) executed blind, and autonomous path selection; a single 20 MHz RAD6000 under VxWorks ran all rover software (planetary rover). [C3-S15, section 3 and 3.3, pp. 48, 50]
- PX4 describes its multicopter controller as "a standard cascaded control architecture" (position → velocity → attitude → angular rate); all loops take their estimates from one estimator (EKF2), and depending on the flight mode the outer position loop is bypassed by a multiplexer placed after it (drones). [C3-S40, "Multicopter Control Architecture"]
- PX4 rover firmware unlocks drive modes one layer at a time — rate tuning (acro mode), then attitude (stabilized), velocity (position mode) and position (auto modes) — and warns that "a drive mode will only work properly if all the configuration for the preceding modes has been completed" (ground rovers, including skid/tank-steered). [C3-S41, `index.md` table and warning]
- ROS's interface convention for velocity commands is REP 103: SI units (metre, radian; derived units such as m/s and rad/s), right-handed frames, body axes x forward, y left, z up; the REP states that inconsistent units and conventions are "a common source of integration issues" and bugs. [C3-S52, "Rationale", "Units", "Axis Orientation"]

### 2. Cascade control theory and extra corrections below the controller (general)
- In an inner/outer design the inner loop is designed first to give "fast and accurate" control, and the outer loop is designed assuming the inner loop is perfect; in Åström & Murray's example the inner bandwidth was 10 rad/s, "10 times that of the outer loop", and the approximation "may not be valid" and must be checked after the design is done. [C3-S01, section 11.6, pp. 341–342]
- A vertical (layered, cascade) decomposition depends on sufficient time-scale separation τc1/τc2 between neighbouring layers; Shinskey recommends at least 4, Skogestad & Postlethwaite and Smith at least 5; "if the time scale separation gets too small, typically 3 or less, the layers (loops) start interacting and resonance occurs … such that performance degrades even nominally". [C3-S03, section 2.5, p. 9]
- A large separation is desired "to avoid potential undesired interactions ('fighting')" and gives robustness to gain changes; a separation of 10 or larger is often recommended, with the rule of thumb 4 (minimum) to 10 (preferable); too large a separation "eats up" the available time window when many layers are stacked. [C3-S03, section 2.5, p. 9]
- The closed-loop response time of the inner loop (τc2) appears as an effective delay to the outer loop, and a gain drop in the inner process slows the inner loop and reduces the separation. [C3-S03, section 2.5, p. 9]
- The accepted benefits of an inner (secondary) loop are: disturbances inside it are corrected before they reach the primary variable, it reduces phase lag seen by the outer loop, it overcomes gain variations within its own loop, and it allows exact manipulation of the secondary variable (Shinskey, quoted). [C3-S03, section 3.2, p. 12]
- If the desired separation of about 4 cannot be achieved, cascade can still be used but these advantages are lost "at least to some degree"; an alternative is to design one controller using both measurements (e.g. state feedback, LQG or MPC). Controllers in a cascade should be tuned sequentially, inner first. [C3-S03, section 3.2, pp. 12–13]
- Anti-windup is needed whenever a controller's output is disconnected from the process for some time: input saturation, selective control where another controller overrides the output, and cascade control with saturation in the inner loop; in the cascade case the inner saturation gives an offset in the outer controller's output "which will result in 'wind up' of the integrator" of the outer controller. [C3-S03, section 3.9, p. 20]
- Nav2's maintainer states that the velocity smoother's open/closed-loop option was collected from several ROS 1 smoothers and is "useful in the context of highly delayed or particularly low-quality odometry". Asked whether open loop in both the controller and the smoother would be better, he answered that, with accurate acceleration limits and a fast-responding robot, it "could theoretically be better only if the odometry from the robot is delayed and/or inaccurate (but the robot did actually execute the command accurately and timely)"; otherwise "it could largely be the same". (Level D.) [C3-S23, issue body and first maintainer comment]
- The issue author reported that a closed-loop controller plus a closed-loop smoother performed worse than a closed-loop controller plus an open-loop smoother, and guessed the limits were not set appropriately. (Level D.) [C3-S23, issue body]
- A Nav2 contributor notes that in closed-loop smoothing the previous command must already be reflected in odometry when the next command is computed, and that "the higher the publish frequency of the velocity command, the more difficult it may become to achieve appropriate acceleration and deceleration". (Level D.) [C3-S23, comment by decwest]
- The Nav2 smoother documentation states that if the smoothing frequency outpaces odometry or `odom_duration` is poorly chosen, "the robot can oscillate and/or accelerate slowly due to latency in closed loop mode", and that "when in doubt, open-loop is a reasonable choice for most users". [C3-S19, "Etc (Important Side Notes)"]
- PX4's rover rate controller is an example of an accepted inner closed loop on yaw rate at the bottom of the chain: a feed-forward term maps the yaw-rate setpoint to motor effort using the kinematic model, and a PI feedback term on measured yaw rate "compensates for disturbances such as uneven ground and external forces"; the attitude, velocity and position loops are then built on top of it. [C3-S41, `rate_tuning.md` steps 2–4 and "Rate Controller Structure"]
- PX4 recommends tuning that loop's feed-forward first with P and I set to zero, adding a yaw-rate correction factor that "skid/tank-steered and mecanum rovers will most likely require" (the source's reasons are "wheel misalignments, excessive friction etc."), and only then adding feedback gains. [C3-S41, `rate_tuning.md` step 2 tip]
- PX4 turns the yaw-rate feedback off where it would be unstable: for Ackermann rovers driving backwards the setpoint is mapped open-loop, because reversing a front-steered vehicle is "non-minimum-phase w.r.t to the yaw rate which leads to instabilities when doing closed loop control" (non-minimum-phase: the first response goes the wrong way). [C3-S41, `rate_tuning.md`, "Rate Controller Structure" note]
- In PX4's fixed-wing stack the outer energy controller's performance "is directly affected by the performance of the pitch control loop", and the docs require the attitude controller to be tuned before the outer controller — the inner-first rule in practice. [C3-S40, "Total Energy Control System (TECS)"]
- PX4's multicopter rate controller limits integral authority "to prevent wind up" and saturates its outputs; the attitude loop feeds the reference body rate forward to the rate setpoint to remove the lag of a pure proportional outer loop. [C3-S40, "Multicopter Angular Rate Controller", "Multicopter Attitude Controller"]

### 3. Command arbitration and hand-over (general and ROS 2)
- In process control, switching a controller between manual and automatic must be "bumpless": the controller's internal state must be made to match so both outputs coincide at the switch; this is easy with incremental-form controllers, and for other forms the idle integrator must track the active output. [C3-S02, section 6.7, "Bumpless Transfer Between Manual and Automatic", pp. 245–247]
- A controller with a tracking input needs no explicit mode-switch signal, because tracking is automatically inactive when the tracking signal equals the controller output; the source notes this "can be used with great advantage when building up complex systems with selectors and cascade control". [C3-S02, section 6.5, "Controllers with a Tracking Mode", p. 231]
- ISO 13849-1 lists "control modes and operating mode selection", "manual reset", "start/restart", "enabling function" and "prevention of unexpected start-up" as distinct safety functions. [C3-S09, Table 5.1, p. 29]
- twist_mux gives each input topic a priority in the range 0–255 (higher wins) and a timeout; an input whose last message is older than its timeout is ignored ("masked"), and a timeout of 0.0 means the input never expires. [C3-S24, `topic_handle.hpp` lines 83, 104–113; C3-S25, `twist_mux_topics.yaml` comments]
- A twist_mux lock is a `std_msgs/Bool` topic with its own priority; while a lock is true — or while its publisher has stopped for longer than its timeout, if the timeout is non-zero — every input with a lower priority is masked. Inputs with priority equal to the lock are not masked, so the example config gives the "pause" lock the joystick's priority "so it'll not block it". [C3-S24, `topic_handle.hpp` lines 189–193, 285–287; C3-S25, `twist_mux_locks.yaml`]
- twist_mux forwards a message only inside the receiving callback, and only if that input is currently the highest-priority unmasked input; there is no timer that publishes zero, so when all inputs time out or a lock engages the mux simply goes silent. [C3-S24, `topic_handle.hpp` lines 195–206; `twist_mux.cpp` lines 140–143, 203–224]
- twist_mux measures message age by arrival time (`stamp_ = mux_->now()` in the callback), not by the message header stamp. [C3-S24, `topic_handle.hpp` lines 195–198, 241–244]
- Clearpath's ROS 2 platform config ranks inputs RC teleop 12, joystick 10, interactive marker 8, external `cmd_vel` (autonomy) 1, all with 0.5 s timeout, and an `e_stop` lock at priority 255 with timeout 0.0 — i.e. any human teleop overrides autonomy and the platform e-stop blocks everything. [C3-S29, `twist_mux.yaml` lines 4–18]
- Autoware's gate enforces "transition guards during mode changes into autonomous driving (e.g., remote→autonomous, manual→autonomous) to limit sudden changes", with a separate set of `on_transition.*` limits active in the transition mode (car domain). [C3-S32, "Main Functionality" and parameter table]
- Autoware keeps turn-indicator, hazard and gear commands unchanged after a gate-mode change "until the topics of new input commands arrive" to ensure continuity of commands. [C3-S32, "Commands on Mode changes"]
- The standard ROS joystick teleop node uses a deadman ("enable") button by default (`require_enable_button: true`): commands are published only while the button is held, and on release it sends "a single no-motion command in order to stop the robot", then stays silent. [C3-S44, README "Parameters"; `teleop_twist_joy.cpp` lines 382–414]
- That node "provides no rate limiting or autorepeat functionality" — a held stick keeps producing commands only if the joystick driver repeats messages, which matters for downstream timeouts. [C3-S44, README "Overview"]
- Nav2's smoother, in open-loop mode, takes its "current velocity" from its own last output; only in closed-loop mode does it read odometry. So in open loop it has no knowledge of motion commanded by another source, while closed loop starts from the measured velocity. [C3-S20, lines 268–274]
- Autoware's emergency-stop operator takes "the control command output from the last node of the control component" as the initial value of its stop command, so the stop ramps down from what was actually being sent (car domain). [C3-S47, `mrm_emergency_stop_operator` README "Input"]
- A formally verified fail-operational concept for automated cars uses five modes (Nominal, Detour, Comfort Stop, Safe Stop, Emergency Stop); the safety channel runs on "hot standby", monitoring but not sending commands, and before a Safe Stop it "first powers off the VC function controller to prevent it producing any arbitrary output" (car domain). [C3-S53, sections 5–5.5, Figure 2]
- IGVC AutoNav rules forbid remote control by a human during competition and require a safety light that is solid when powered and flashing in autonomous mode, returning to solid "as soon as the vehicle comes out of autonomous mode" (student ground vehicles). [C3-S39, section I.2, p. 5]

### 4. Emergency stop and safety architecture (general)
- An emergency stop is not a safeguard but a "complementary protective measure"; it should take effect when guards and protective devices have failed or been defeated, and "under no circumstances may complementary protective measures influence the function and standard of safeguards". [C3-S09, section 5.5, p. 34]
- ISO 13849-1 lists "function for stopping in an emergency" implemented with STO or SS1, i.e. a category 0 or category 1 stop. [C3-S09, Table 5.1, p. 29; Table 5.2, p. 30]
- The Performance Level required (PLr) for each safety function comes from risk assessment; Rockwell's worked emergency-stop example requires category 3, PL d. [C3-S36, p. 5]
- In the ISO 13849 Category 2 designated architecture (functional channel plus test equipment, TE), "the part of the test equipment evaluating the diagnostic results must however normally be engineered external to the functional channel, for example in the form of a separate watchdog". "Complete merging of TE with the functional channel is not acceptable", for example an on-chip watchdog without the separation described in IEC 61508-2, Annex E, "or test equipment that is engineered only in the form of software and accesses OTE directly by means of a de-energizing signal generated by software" (OTE: the output of the test equipment). [C3-S09, section 6.2.5, p. 52]
- For category 2 architectures the test rate must be at least 100 times the demand rate on the safety function, or the test must run on demand and the fault-detection-plus-safe-state time must be shorter than the time to reach the hazard (see EN ISO 13855). [C3-S09, section 6.2.5, p. 52]
- IEC 61508 assigns one of four Safety Integrity Levels (SIL 1–4) to each safety function; the SIL is "a property of a safety function", not of a device, and SIL bands correspond to risk-reduction factors (SIL 1: >10 to ≤100 … SIL 4: 10,000 to ≤100,000). [C3-S10, slides 14–16]
- IEC 61508 introduced SILs largely because of systematic failures (specification errors, software errors, human error, EMI), not only random hardware failures. [C3-S10, slides 12–13]
- The Clearpath Husky A200 motion stop cuts power to the motor drivers through a normally-open relay in series with the stop switch; commands received during stop are "not buffered", but if commands continue the robot "will move at the speed commanded once the stop is released", and "there is no second 'start' action required" (field robot). [C3-S30, "Stop Button and Lockout"]
- The newer Husky A300 requires all e-stops to be released and a separate Safety Restart button to be pressed; its e-stop buttons are rated PLc and its electrical braking on e-stop PLa per ISO 13849; the wireless e-stop is "asserted automatically if the robot is not able to communicate wirelessly with the controller" (field robot). [C3-S31, "Safety System Functionality", "Emergency Stop Buttons", "Wireless Emergency Stop"]
- Rockwell's example: after an e-stop, "hazardous motion cannot be restarted until the E-stop is released and the Reset button is pressed and released"; if the SS1 or brake-control functions fault, recovery needs two resets. [C3-S36, p. 6]
- Clearpath states that the Husky "should not be used" with the stop system as "the means of controlling robot motion during regular operation", and advises "never assume that the robot can be reliably stopped on command". [C3-S30, "Stop Button and Lockout", "Recommended Safe Work Procedures"]
- IGVC rules require both a mechanical e-stop (red push-to-stop, at least 1 inch, centre rear, 2–4 ft above ground) and a wireless e-stop effective to at least 100 ft; both "must be hardware based and not controlled through software" and must "bring the vehicle to a quick and complete stop"; judges hold the wireless e-stop during runs (student ground vehicles). [C3-S39, section I.2, p. 5]
- ANSI/RIA R15.08 (released December 2020) covers "industrial mobile robots", including both AGVs (fixed routes) and AMRs (sensor-based obstacle avoidance), and builds on ANSI/RIA R15.06 (industrial robots) and ANSI/ITSDF B56.5 (guided industrial vehicles); its three parts address manufacturers, integrators and end users. [C3-S45, section 2 and Table 1, p. 2]
- ISO/TS 15066's four collaborative modes — safety-rated monitored stop, hand guiding, speed and separation monitoring, power and force limiting — are proposed as transferable to mobile robots working alongside people; national and local regulations take precedence over industry standards. [C3-S45, section 2, p. 2]
- Autoware's MRM (minimal-risk manoeuvre) handler issues an emergency stop if the system-availability topic is missing for more than 0.5 s; with `use_emergency_holding` it never returns to normal on its own, and an emergency lasting longer than `timeout_emergency_recovery` (5.0 s) is also not recovered automatically — a latched emergency (car domain). [C3-S47, `mrm_handler.schema.json`]
- In the fail-operational car concept, monitoring is layered: application deadlocks, OS crashes, stuck schedulers, silent actuators and network faults are each detected by heartbeats, watchdogs or challenge-response checks run by a separate layer, and the vehicle-level safety monitor runs on a separate safety controller. [C3-S53, section 4 and Table I]

### 5. Placement and consistency of speed and acceleration limits (general and ROS 2)
- Limits appear at several layers in the reference stack: velocity and acceleration constraints inside trajectory-optimising controllers such as TEB to keep trajectories "dynamically feasible"; the smoother's `max_velocity`, `max_accel`, `max_decel` and `deadband_velocity`; the collision monitor's slowdown/limit/approach zones; and diff_drive_controller's per-axis velocity/acceleration/jerk limiter. [C3-S05, section IV, p. 7; C3-S18; C3-S21, "Features"; C3-S27, "Task-space velocity, acceleration and jerk limits"]
- The purpose of the Nav2 smoother is to "reduce wear-and-tear on robot motors and hardware controllers by smoothing out the accelerations/jerky movements that might be present with some local trajectory planners' control efforts". [C3-S19, intro]
- Autoware states that its final gate filter "is not designed to enhance ride comfort"; its purpose is to "detect and remove abnormal values", and "if this filter is frequently active, it implies the control module may need tuning"; smoothing belongs in the control module (car domain). [C3-S32, "Filter function"]
- The smoother applies separate acceleration and deceleration limits, treating a change as deceleration whenever the command magnitude falls or the sign changes; the per-step change is clamped to `accel/smoothing_frequency`. [C3-S20, lines 225–246]
- With `scale_velocities` the smoother scales all axes by the same factor so the command keeps its direction, "even if it means deviating off commanded trajectory slightly"; diff_drive_controller has an analogous `preserve_turning_radius` option (used by Clearpath). [C3-S18, `scale_velocities`; C3-S29, `a200/control.yaml` line 40]
- The deadband zeroes commands below a threshold "to prevent small commands from damaging hardware controllers if that speed cannot be achieved due to stall torque"; the README adds it is useful when breakaway torque from standstill is high "so sending very small values will pull high amounts of current". [C3-S18, `deadband_velocity`; C3-S19, "Etc"]
- In open-loop mode the smoother uses its own last output as the current velocity, which the documentation says is a good assumption "when acceleration limits are set appropriately" — i.e. only if the smoother's limits are at or below what the base can actually deliver. [C3-S18, `feedback`; C3-S20, lines 268–273]
- Nav2's maintainer notes that some controllers (RPP, Graceful) do not use the input velocity, while DWB and MPPI "consider the dynamic limitations from the current speed when calculating the next trajectory", so the feedback choice matters more for them. (Level D.) [C3-S23, first maintainer comment]
- Clearpath's base controller applies its own limiter: in the A200 config, diff_drive_controller limits linear x to 1.0 m/s and 1.0 m/s² and angular z to 1.0 rad/s and 1.0 rad/s². [C3-S29, `a200/control.yaml` lines 49–68]
- Nav2's Marathon 2 experiment capped both robots at 0.45 m/s "for functional safety, below their maximum allowable speed". [C3-S04, section V, p. 6]
- IGVC enforces a 5 mph maximum that must be "hardware governed", with no changes to the speed-control hardware after qualification, and a 1 mph minimum average speed — the hard speed limit is placed below all software (student ground vehicles). [C3-S39, section I.2, p. 5]
- PX4 separates the hard velocity saturation (`MPC_XY_VEL_MAX`, "the maximum possible horizontal velocity") from the desired cruise speed of each mode (`MPC_XY_CRUISE`, `MPC_VEL_MANUAL`) (drones). [C3-S40, "Multicopter Position Controller"]
- PX4 sets the rover yaw-rate limit from what the vehicle can physically do: either the highest yaw rate that does not lift the wheels, or the maximum yaw rate measured in a full-throttle, full-steer test; yaw acceleration and deceleration limits are separate optional parameters. [C3-S41, `rate_tuning.md` steps 1 and 5]
- Nav2's own defaults are not identical across layers: MPPI defaults to `ax_max` 3.0 m/s², `ax_min` −3.0 m/s², `az_max` 3.5 rad/s², while the velocity smoother defaults to 2.5 m/s² accel, −2.5 m/s² decel and 3.2 rad/s² angular accel (MPPI page is the rolling-release documentation). [C3-S49, `ax_max`, `ax_min`, `az_max`; C3-S18, parameter list]
- MPPI's `clamp_raw_controls` applies acceleration limits to the raw sampled controls, and the docs warn it "may cause issues if `ax_max` && `ax_min` are very asymmetric". [C3-S49, `clamp_raw_controls`]
- Nav2's smoother rejects any input command containing NaN or Inf ("Ignoring as invalid"), a basic abnormal-value filter. [C3-S20, lines 184–188]
- Autoware's emergency stop is itself limited: it runs at 30 Hz with a target deceleration of −2.5 m/s² and a jerk of −1.5 m/s³ (car domain). [C3-S47, `mrm_emergency_stop_operator.param.yaml`]

### 6. Stale commands, timeouts, watchdogs and heartbeats (general and ROS 2)
- WPILib (FRC robots) gives each actuator its own "Motor Safety" watchdog: if `set()`/`feed()` is not called within the timeout (default and "minimum useful" value 100 ms) the output is disabled; timers are checked every 5 received Driver Station packets (100 ms nominal); it is on by default for drive-train classes because a drive "latched on a particular value" can cause damage. [C3-S43, "Motor Safety"]
- On top of that, the FRC system watchdog (network code plus FPGA) "will disable all actuator outputs if it does not receive a valid data packet for 125ms" — a second, independent timeout layer. [C3-S43, "Motor Safety"]
- MER mobility software used command limits including "prescribed time limitations on the duration of motion command execution" and a latest time of day for all mobility commands, halting when commands take longer than expected (planetary rover). [C3-S15, section 3.2, pp. 49–50]
- Nav2 smoother: after `velocity_timeout` (default 1.0 s) with no new command it sets its target to zero, decelerates at `max_decel`, and once the output is zero it stops publishing. [C3-S18, `velocity_timeout`; C3-S20, lines 257–264]
- diff_drive_controller: on every update it compares the command's header stamp with the current time and, if the age exceeds `cmd_vel_timeout` (default 0.5 s; 0.0 disables), sets linear and angular command to zero, which then passes through the acceleration limiter. [C3-S28, `diff_drive_controller.cpp` lines 124–133, 237–245; `parameters.yaml` lines 99–103]
- For unstamped `Twist` input, diff_drive_controller stamps the message with the current time on receipt; a `TwistStamped` with a zero stamp is also re-stamped with "now" and a warning is logged. [C3-S28, `diff_drive_controller.cpp` lines 357–363, 384–386]
- When the controller is deactivated it writes zero velocity to all wheel command interfaces (`halt()`). [C3-S28, `diff_drive_controller.cpp` lines 105–112, 547–558]
- Collision Monitor stops the robot if any data source has not produced new data within `source_timeout` (default 2.0 s), and stops publishing zero after `stop_pub_timeout` so other systems can take over. [C3-S22, `source_timeout`, `stop_pub_timeout`]
- ROS 2 QoS offers Deadline (maximum expected time between messages), Lifespan (maximum age before a message is dropped), and Liveliness with a lease duration; the middleware raises events such as "requested deadline missed" and "liveliness changed" to the application. [C3-S33, "QoS policies", "QoS events"]
- The design article states deadlines are tracked "only up to the rmw layer", a deadline of 0 disables tracking, and a subscriber's requested deadline must be ≥ the publisher's offered deadline for them to connect. [C3-S34, "Deadline"]
- Autoware's gate checks heartbeat topics for its inputs, has a `system_emergency_heartbeat_timeout` and an `external_emergency_stop_heartbeat_timeout`, and "will not start" without the external heartbeat topic when that check is enabled (car domain). [C3-S32, parameters and "External Emergency Heartbeat"]
- Husky A200 shows a red communication light when "serial communications are currently timed-out", and will not drive without a stream of correctly formatted commands (field robot). [C3-S30, "Status Panel"]
- The REV SPARK MAX motor controller disables its output if "a valid signal isn't received within a 60ms window" (PWM interface) and then brakes or coasts according to its idle mode. [C3-S48, `control-interfaces.md`, "PWM Interface"]
- The `twist_stamper` package converts `Twist` to `TwistStamped` by setting the stamp to the converting node's clock at conversion time, so a stamp added this way records when the converter saw the message, not when the command was produced. [C3-S51, README; `twist_stamper.py` line 48]

### 7. Stopping behaviour: braking, coasting, holding zero (general)
- IEC 61800-5-2 drive stop functions (as tabulated by IFA): STO — motor receives no energy capable of producing rotation, stop category 0; SS1 — motor decelerates (ramp monitored, then STO at standstill, or STO after a timeout), stop category 1; SS2 — same but ending in SOS, stop category 2; SOS — "motor is stationary and resisting external forces"; SLS/SLA — safely-limited speed/acceleration. [C3-S09, Table 5.2, p. 30]
- STO provides a category 0 stop — "power is removed immediately from the motor" — and "does not provide braking"; if braking is required, the drive must first stop the motor conventionally and then STO is applied. [C3-S37, "Capabilities" item 2 and "Limitations" item 2, pp. 13–14]
- With torque removed, "the machinery normally coasts to a halt", but some applications can move from the loss of torque (e.g. gravity). [C3-S37, p. 9]
- In Rockwell's category 1 e-stop, SS1 monitors deceleration to a configured standstill speed, then a safety brake is engaged and STO is applied; a fault in SS1 triggers immediate STO plus brake. [C3-S36, p. 6]
- In a brushed-DC H-bridge, "slow decay" (both low-side switches on) shorts the winding, which collapses the back-EMF and "results in a very quick rotor stop"; "fast decay" drives the current to zero as fast as possible through the opposing switches or diodes. [C3-S38, sections 2.1–2.2, pp. 4–6]
- Husky A300 applies an electrical (resistive) brake when the e-stop is engaged, but payload mass and slope still affect terminal speed, and in e-stop on a slope the robot can roll (field robot). [C3-S31, "Important System Limits", general warnings]
- ISO 3691-4 requires the braking-system control function at PLr d and parking-brake control at PLr b, and its personnel-detection function requires the truck to "stop before contact … with a stationary person", which forces assessment of the whole detection-plus-braking system (AGV). [C3-S11, pp. 6, 8]
- Nav2's smoother and diff_drive_controller both implement a timeout stop as a ramped deceleration (zero target through the limiter), not an instant cut. [C3-S20, lines 257–264; C3-S28, lines 124–133, 237–245]
- For vehicles, SICK's safety-scanner manual defines stopping distance as SA = SBr + SAnF + SAnS: braking distance, plus distance travelled during the vehicle control's response time "(incl. signal propagation time)", plus distance travelled during the sensor's response time (tR × Vmax); braking distance grows with the square of speed, not linearly (AGVs). [C3-S46, section 5.3.10.3, pp. 38–39]
- The protective-field length adds supplements to the stopping distance: SL = SA + TZ + ZR + ZF + ZB (sensor tolerance, reflection error, lack of ground clearance — 150 mm when clearance is under 120 mm — and "decreasing braking force of the vehicle"); turning must be considered separately, and each speed-dependent field is calculated separately. [C3-S46, sections 5.3.10.1–5.3.10.4, pp. 37–39]
- For stationary machines the same manual gives the ISO 13855 form S = 1,600 mm/s × T + TZ + ZR + CRO, where T is the stopping time of the whole system, including control response and signal propagation. [C3-S46, section 5.3.7.3, p. 30]
- A motor controller's idle mode decides what "zero" means physically: in brake mode the SPARK MAX "will effectively short all motor wires together", bringing the motor "to a quick stop"; coast mode disconnects the windings so the motor spins down on its own; the idle mode applies both to a neutral command and to loss of signal. [C3-S48, `operating-modes.md` "Brake/Coast Mode"; `control-interfaces.md` "PWM Interface"]
- In the fail-operational car concept the last-resort Emergency Stop mode "simply sends braking commands to the vehicle actuators to blindly stop the vehicle as quickly as possible", with comfort no longer guaranteed, while Comfort Stop and Safe Stop are controlled pull-overs (car domain). [C3-S53, sections 5.3–5.5]

### 8. Loop rates, latency and jitter (general and ROS 2)
- A time delay τ adds phase lag ωτ that grows linearly with frequency; a long delay acts like a slow right-half-plane zero at z ≈ 2/τ, and for a right-half-plane zero the crossover frequency is limited to ωgc < 0.6·z (with 60° allowable phase lag). [C3-S01, section 9.4, p. 283; section 11.5, pp. 332–333]
- Sampling adds on average h/2 delay if computation is organised to read-compute-write immediately; in practice "the delays introduced because of the sampling is often several sampling periods". [C3-S02, section 6.7, "Sampling", p. 238]
- ROS 2's default single-threaded executor (analysed for Crystal) checks timers first, then subscriptions, services and clients, in registration order; messages arriving during a processing window are not considered until the next polling point, which "leads to priority inversion", and each non-timer callback runs at most once per window. [C3-S07, section 3, p. 6:6]
- In a multi-node ROS 2 test, end-to-end latency "strongly depends on the used DDS middleware", ROS 2 can add 50 % latency over raw DDS, the DDS layer and the delay between message notification and retrieval are the largest contributors, and latency depended heavily on CPU energy-saving features. [C3-S12, abstract and section 5]
- Composition and intra-process communication "cut significantly" latency, CPU use and send-rate limits compared with separate processes; inter-process latency stayed below 1 ms up to 1 MB messages on the test machine. [C3-S13, section III, p. 6]
- In a 1-hour cyclictest, worst-case scheduling latency was 13197 µs on a vanilla kernel, 110 µs with PREEMPT_RT, and 88 µs with PREEMPT_RT plus an isolated CPU; with concurrent network traffic, real-time priority alone was not enough and the application and its network interrupt had to be pinned to the same CPU. [C3-S14, section IV-A to IV-C and Tables I–IV]
- Real-time systems are defined by a deterministic schedule, not by low latency; real-time code should pre-allocate memory, lock it (`mlockall`) and avoid page faults in the loop. [C3-S35, "Definition of Real-time Computing", "Memory management"]
- ros2_control's controller manager tries to run its loop with `SCHED_FIFO` priority 50, needs `rtprio`/`memlock` limits for the user, and the docs recommend a real-time or low-latency kernel because "the normal linux kernel is optimized for computational throughput". [C3-S26, "Determinism"]
- Nav2's smoother can run at a higher rate than the controller to interpolate (e.g. controller at 20 Hz, smoother at 100 Hz giving about 5 messages per controller step), and offers `use_realtime_priority` (thread priority 90). [C3-S19, "Design"; C3-S18, `use_realtime_priority`]
- Reference rates found: Clearpath A200 controller manager `update_rate` 50 Hz; Nav2 smoother default 20 Hz; MPPI "1000 samples at 50 Hz or 2000 samples at 30 Hz"; MER pose estimate updated at 8 Hz while driving. [C3-S29, `a200/control.yaml` line 3; C3-S18, `smoothing_frequency`; C3-S05, section IV, p. 8; C3-S15, section 3.2, p. 49]
- Nav2's maintainer states that odometry "for real hardware robots is typically at about 100hz or higher" and the collision monitor recommends odometry of about 100 Hz for its motion compensation, which adds about `1/(2*odom_rate)` delay per cycle. [C3-S23, maintainer comment; C3-S22, `base_shift_correction`]
- Control-timing terms: *sampling latency* is the delay from the task's release to when it samples; *sampling jitter* is the spread (max − min) of that latency; *input-output latency* is the delay from sampling to actuation, and its spread is the *input-output jitter*. [C3-S42, section 2.3, pp. 41–42]
- A constant input-output latency reduces phase margin and limits achievable performance but can be analysed with standard linear tools and designed for, so "a constant input-output latency is preferable over a varying latency"; varying latency needs special analysis (jump-linear systems, Jitterbug). [C3-S42, section 2.3, pp. 42–43]
- A standard way to shorten input-output latency is to split the control code into "Calculate Output" (only what uses the new sample, sent immediately) and "Update State" (done after the output is sent). [C3-S42, section 2.3, p. 43]
- Rule of thumb: sampling-interval variations smaller than 10 % of the nominal period "need not be compensated for". [C3-S42, section 2.3, p. 48]
- Being schedulable (meeting deadlines) does not guarantee control performance; in the thesis's example the controller was "quite sensitive to input-output latency but not very sensitive to jitter". [C3-S42, ch. 1, p. 22]
- In ROS 2 releases after Dashing, a timer callback is skipped if the executor starts it later than one full period after the previous one — unlike classical periodic-task theory, where every job runs; the executor's rules changed across releases (Foxy to Iron described; Jazzy moving toward FIFO order). [C3-S50, section 2, p. 1:7]
- Response-time analysis of processing chains found that a chain's end-to-end latency "is primarily affected by the priority of its final (sink) callback", leading to the advice to raise sink priority (Tang et al., summarised by the survey). [C3-S50, section 3.1, p. 1:13]
- Two end-to-end metrics are used for cause-effect chains: *maximum reaction time* (external event → reaction) and *maximum data age* (how old the input behind an actuation can be); after warm-up the two were proven equivalent (Günzel et al.), and an optimiser for executor assignment, DDS mode, priorities and timer periods cut measured maximum latency by 19.8 % on an autonomous-racing stack. [C3-S50, section 3.1, p. 1:14]
- Nav2's MPPI documentation says `model_dt` "should be set to the duration of your control frequency" (0.05 s at 20 Hz) and may be lower "but not larger", and that odometry should publish "at least as fast as your control frequency (ideally much faster)" when acceleration limits are low. [C3-S49, "Notes to Users"]
- A motor controller's feedback also has its own period: SPARK MAX status frames default to 10 ms (applied output, faults), 20 ms (velocity, current, voltage) and 20 ms (position), configurable from 1 ms, and the setting "does not persist" through a power cycle. [C3-S48, `control-interfaces.md`, "Periodic Status Frames"]

### 9. Measuring and testing the pipeline (general)
- ros2_tracing instruments ROS 2 with LTTng tracepoints to recover callback durations, timer intervals and message flow; with all ROS 2 instrumentation enabled (about 10 tracepoints per message), its measured mean end-to-end message-latency overhead was 0.0033 ms (50 % of samples between 0.0010 and 0.0056 ms). [C3-S08, sections V–VI]
- Kronauer et al. measure latency from publish in the first node to the subscriber callback in the last node, patching timestamps into each layer of the ROS 2 call stack, and report the 95th percentile rather than the mean. [C3-S12, sections 3.3–3.4]
- Gutiérrez et al. judge real-time communication by worst-case latency, missed deadlines and packet loss over a 3-hour round-trip test at 1 ms period, using `cyclictest` for the OS baseline and `ftrace` to find the source of spikes. [C3-S14, section IV-A to IV-C]
- Nav2's maintainer suggests measuring command latency by comparing actual speed with commanded speed and plotting both over time. (Level D.) [C3-S23, maintainer comment]
- Clearpath recommends first tests "up on blocks" and at low speed, and testing safety functions after shipping per the maintenance manual. [C3-S31, "General Warnings", "Safety System Functionality"]
- Rockwell provides a verification and validation checklist per safety function and computes the achieved PL with SISTEMA. [C3-S36, pp. 5, 25–27]
- PX4's tuning method for the rover's inner loop is to hold stick inputs at several levels, then plot the setpoint and the measured yaw rate from the flight log over each other and adjust gains until tracking is acceptable. [C3-S41, `rate_tuning.md` steps 2–3]
- IGVC qualification checks e-stop location, wireless e-stop effectiveness at 100 ft, and minimum and maximum speed over a prescribed distance. [C3-S39, section I.4 "Qualification", pp. 6, 8]
- The formal fail-operational car study verified its mode-switching logic by model checking (mCRL2, modal mu-calculus) instead of road tests, because exhaustive coverage of multiple-fault combinations is "intractable" by testing or simulation. [C3-S53, abstract]

### 10. How other vehicle types do it
- Cars (Autoware): the gate selects among autonomy, external/remote and emergency commands, enforces speed-dependent final limits on acceleration, jerk, steering and steering rate, and applies a separate set of limits during transition into autonomous mode. [C3-S32]
- AGVs (ISO 3691-4 via TÜV): 27 safety functions each with a minimum PLr; ISO 3691-4 adds a "confined zone" to EN 1525's restricted and hazard zones and sets per-zone requirements such as maximum speed, e.g. 0.3 m/s where personnel detection is muted; in some cases automatic restart without personnel detection is permitted if side or forward clearance is > 500 mm and this is "determined to be acceptable by a risk assessment". [C3-S11, pp. 6–7]
- Planetary rovers (MER): three layers of safety checks — command limits (duration, time of day, repetition limits), reactive checks (motor current, tilt, suspension, actuator range thresholds, motor stalls) and predictive vision-based hazard checks; "Guarded Motion" uses terrain assessment as a predictive check before directed commands. [C3-S15, section 3.2, pp. 49–50; C3-S16, section 2, p. 3]
- Planetary rovers (MER): directed drives ran without onboard compensation for drift, visual-odometry drives updated position, and local path selection corrected for heading changes; the paper says these driving modes "were used during the first three years of operation" and summarises the capabilities available after the September 2006 software update. [C3-S16, p. 1]
- Teleoperation under delay: operators adopt "move and wait" (Ferrell and Sheridan), which works but is slow; supervisory control gives the remote robot small autonomous subtasks; one study found 100–250 ms delays made no significant difference while >400 ms degraded surgeon performance. [C3-S17, sections 2.1–2.2, pp. 2–3]
- Drones and ground rovers (PX4): nested loops position → velocity → attitude → rate with a mode multiplexer after the outer loop, integrator limits in the rate and velocity loops, and a hard velocity cap separate from the desired cruise speed. [C3-S40; C3-S41]
- Cars (fail-operational concept): a nominal channel and an independent safety channel on hot standby, a five-mode degradation policy from detour down to a blind emergency stop, and heartbeats/watchdogs between layers. [C3-S53, sections 3–5]
- AGVs (safety laser scanners): speed-dependent protective fields sized from total stopping distance, including control-system response time and braking-force loss. [C3-S46, section 5.3.10]
- Competition robots (FRC/WPILib): per-actuator watchdogs of 100 ms plus a 125 ms system watchdog. [C3-S43]
- Construction-site mobile robots (Clearpath Jackal case study): standards mapping from ISO 10218, ISO/TS 15066, ANSI/RIA R15.08 and ANSI/ITSDF B56.5, with emergency-stop devices and speed reduction among the mitigations. [C3-S45, Table 1 and risk table]

### 11. ROS 2 / product-specific implementations
- **twist_mux**: priorities clamped to 0–255; an input with priority ≤ 0 "will never be selected"; a lock with priority ≤ 0 is redundant because "priority 0 is always locked". Example config: joystick and tablet 100, keyboard 90, navigation 10, all 0.5 s. [C3-S24, `topic_handle.hpp` lines 83, 176–182, 269–274; C3-S25, `twist_mux_topics.yaml`]
- **Nav2 velocity_smoother** defaults: 20 Hz, OPEN_LOOP, max velocity [0.5, 0.0, 2.5], max accel [2.5, 0.0, 3.2], max decel [−2.5, 0.0, −3.2], `velocity_timeout` 1.0 s, `odom_duration` 0.1 s; limits are signed, so decelerations must be negative. [C3-S18, parameter list and example]
- **Nav2 collision_monitor**: stop, slowdown, limit and approach models; when several zones trigger "the most aggressive one is used"; it "does not provide hard real-time safety certifications". [C3-S21, "Collision Monitor", "Features"; C3-S22, "Features"]
- **ros2_control diff_drive_controller** (Humble): subscribes to `~/cmd_vel` (TwistStamped, `use_stamped_vel: true`) or `~/cmd_vel_unstamped`; can publish the limited command on `~/cmd_vel_out` (`publish_limited_velocity`); limits are per axis and ignore position limits. [C3-S27, "Subscribers", "Publishers", parameters]
- **Clearpath A200 (ROS 2)**: controller manager 50 Hz, diff_drive `cmd_vel_timeout` 0.5 s, `open_loop: false`, `preserve_turning_radius: true`, velocity and acceleration limits enabled, jerk limits disabled. [C3-S29, `a200/control.yaml`]
- **teleop_twist_joy** (ROS 2 Humble): deadman button required by default; one zero command on release; optional turbo button; can publish `TwistStamped` (`publish_stamped_twist`). The README gives `enable_button` default 0, while the Humble source declares default 5. [C3-S44, README "Parameters"; `teleop_twist_joy.cpp` lines 104–106]
- **twist_stamper**: two nodes, `twist_stamper` (Twist → TwistStamped, stamp = node clock "now", `frame_id` parameter default empty) and `twist_unstamper`. [C3-S51]
- **Autoware MRM handler**: 10 Hz update, 0.5 s availability timeout, optional comfortable stop or pull-over for latent faults, optional emergency holding. [C3-S47, `mrm_handler.schema.json`]
- **REV SPARK MAX**: 60 ms signal-loss window (PWM), brake/coast idle mode applied on neutral command or no signal, periodic CAN status frames at 10–20 ms by default. [C3-S48]
- **WPILib Motor Safety**: enabled by default for all drive objects, disabled for other motor controllers and servos; timeout configured per actuator in seconds, not globally; default 100 ms. [C3-S43, "Motor Safety"]

## Recommended practice
What the sources recommend, in order along the chain:
1. Keep each lower loop 4–10× faster (in closed-loop time constant) than the loop above it; if that is not possible, either accept that the cascade's advantages are lost "at least to some degree" or design a single controller that uses both measurements (e.g. LQG or MPC). [C3-S03, sections 2.5 and 3.2, pp. 9, 12–13]
2. Tune inner loops first, then outer loops using the closed inner loop as the plant, and check the "inner loop is perfect" assumption afterwards. [C3-S03, section 3.2, p. 13; C3-S01, section 11.6, p. 342]
3. Apply anti-windup in the outer controller whenever an inner loop can saturate or be overridden. [C3-S03, section 3.9, p. 20]
4. Order the ROS 2 chain controller → velocity smoother → collision monitor → base controller. [C3-S19, "Design"; C3-S22, `cmd_vel_in_topic`]
5. Use open-loop smoothing unless odometry is high-rate and low-latency relative to the smoothing rate; never run a closed-loop smoother faster than odometry. [C3-S19, "Etc"]
6. Treat the last limiter as a guard that should rarely activate, not as a comfort filter; frequent activation means the upstream controller needs tuning. [C3-S32, "Filter function"]
7. Give every source a timeout at the mux and give the base controller its own command timeout, because the mux goes silent rather than sending zero. [C3-S24, `twist_mux.cpp` lines 140–143; C3-S28, lines 124–133; C3-S29]
8. Implement the e-stop as a category 0 or 1 stop (STO or SS1) that is hardware based and not controlled through software, and require a deliberate reset before motion resumes. Where a Category 2 architecture with testing is used, put the diagnostic evaluation outside the functional channel (e.g. a separate watchdog). [C3-S09, pp. 29–30, 52; C3-S39, p. 5; C3-S31, "Emergency Stop Buttons"; C3-S36, p. 6]
9. Choose a category 1 stop (controlled deceleration, then power removal) where uncontrolled coasting is a hazard; STO alone does not brake. [C3-S37, p. 14; C3-S36, p. 6]
10. For the control loop, use a real-time or low-latency kernel, real-time thread priority and locked memory, and measure latency with tracing (report worst case or 95th percentile, not just the mean). [C3-S26, "Determinism"; C3-S35; C3-S14, section IV-C; C3-S12, section 3.3]
11. If an inner rate loop is used under the navigation layers, build and tune it first (feed-forward first, then feedback), and enable each outer mode only after the layer below works. [C3-S41, `index.md`, `rate_tuning.md`]
12. Set rate limits from what the vehicle can physically do (measured maximum yaw rate, roll-over limit), and keep the hard cap separate from the desired cruise speed. [C3-S41, `rate_tuning.md` step 1; C3-S40, "Multicopter Position Controller"]
13. Prefer a constant, short input-output latency over a varying one; send the output before doing state updates. [C3-S42, section 2.3, pp. 42–43]
14. Give every drive actuator its own command watchdog (about 100 ms in FRC practice) in addition to a system-level timeout. [C3-S43, "Motor Safety"]
15. Size stopping and protective distances from the total response time — sensor, control system including signal propagation, and braking — with a supplement for loss of braking force, separately for each speed range. [C3-S46, sections 5.3.10.3–5.3.10.4, pp. 38–39]

## Common mistakes
- Adding a feedback loop that is not much faster than the loop above it, so the layers "fight" and resonate even with a correct model. [C3-S03, section 2.5, p. 9]
- Letting an inner loop saturate without anti-windup on the outer controller, which winds up the outer integrator. [C3-S03, section 3.9, p. 20]
- Running a closed-loop smoother faster than odometry or with a poorly chosen `odom_duration`, causing oscillation or slow acceleration. [C3-S19, "Etc"]
- Setting deceleration limits with the wrong sign (they are signed and must be negative), or minimum rotation velocities positive. [C3-S19, "Etc"; C3-S18, `min_velocity`, `max_decel`]
- Assuming twist_mux will send a stop when inputs time out or a lock engages; it only goes silent. [C3-S24, `twist_mux.cpp` lines 140–143]
- Giving a twist_mux input priority 0, which is never selected. [C3-S24, `topic_handle.hpp` lines 176–182]
- Using the e-stop as the normal way to stop, or assuming the robot will always stop on command. [C3-S30, "Stop Button and Lockout", "Recommended Safe Work Procedures"]
- Relying on an e-stop that clears on release alone while commands are still streaming: the robot moves at the commanded speed as soon as the stop is released. [C3-S30, "Stop Button and Lockout"]
- In a Category 2 architecture, merging the test equipment with the functional channel, e.g. software-only test equipment that drives the test-equipment output (OTE) directly by a software-generated de-energizing signal. [C3-S09, section 6.2.5, p. 52]
- Expecting STO to brake; it only removes torque and the machine coasts. [C3-S37, pp. 9, 14]
- Using a final safety limiter to smooth commands, which hides a badly tuned controller. [C3-S32, "Filter function"]
- Tuning an outer mode before the layer beneath it works; PX4 warns that a mode works properly only if all preceding configuration is complete. [C3-S41, `index.md`]
- Closing a yaw-rate loop where the plant is non-minimum-phase (e.g. reversing a front-steered vehicle), which causes instability. [C3-S41, `rate_tuning.md`]
- Assuming a ROS 2 timer callback runs every period; after Dashing a late timer job is skipped. [C3-S50, p. 1:7]
- Treating a deadline-meeting (schedulable) system as good enough; control performance depends on latency, which schedulability does not bound. [C3-S42, p. 22]
- Sizing a stopping or protective distance from braking alone, leaving out sensor and control response times, signal propagation and wear of the brakes. [C3-S46, pp. 38–39]
- Implementing the e-stop in software; the IGVC rules require both e-stops to be "hardware based and not controlled through software". [C3-S39, p. 5]
- Adding stamps with a converter node (e.g. twist_stamper) and then treating the stamp as the command's creation time. [C3-S51]

## Disagreements between sources
- **Reset after emergency stop.** Husky A200 resumes motion immediately when the stop is released with no second start action [C3-S30]; Husky A300 and Rockwell's ISO 13849 example require a separate reset/restart action [C3-S31; C3-S36, p. 6]. The newer, safety-rated designs require the reset.
- **Stale-command detection.** twist_mux judges age by arrival time [C3-S24], diff_drive_controller by message header stamp (with arrival-time stamping for unstamped input) [C3-S28], and the Nav2 smoother by arrival time of the last command [C3-S20, lines 191, 257–258]. The sources do not discuss which is preferable.
- **Open vs closed loop in the smoother.** Not a disagreement: Nav2 docs call open loop "a reasonable choice for most users" [C3-S19], and the maintainer says open loop could theoretically be better only when odometry is delayed or inaccurate while the robot executes the command accurately, and otherwise "could largely be the same" [C3-S23]. No source gives measured evidence for either choice on real hardware.
- **Where to close the yaw-rate loop.** PX4 closes a yaw-rate PI loop at the lowest layer of its rover stack and builds heading, velocity and position loops on it [C3-S41]; in the Nav2 discussion the issue author reported that a closed-loop smoother below a closed-loop controller gave worse results than an open-loop smoother, possibly from badly set limits, and the maintainer expects open and closed loop to give largely the same results unless odometry is delayed or inaccurate [C3-S23]. The two are consistent with cascade theory if the inner loop is designed and tuned as part of the cascade and is much faster [C3-S03], but no source compares the two layouts on the same robot.
- **Documentation vs code (twist_mux).** The twist_mux example topics config says timed-out inputs "use 0.0 speed instead" [C3-S25, `twist_mux_topics.yaml` comment], but the code masks a timed-out input and publishes nothing; it has no zero-publishing path [C3-S24, `topic_handle.hpp` lines 195–206; `twist_mux.cpp` lines 140–143]. The code is what runs.
- **Documentation vs code.** teleop_twist_joy's README gives `enable_button` default 0, while its Humble source declares 5 [C3-S44]; the code is what runs.
- **Default limits across Nav2 layers.** MPPI defaults (3.0 m/s², 3.5 rad/s²) differ from the smoother defaults (2.5 m/s², 3.2 rad/s²) [C3-S49; C3-S18]; neither page states which should be the tighter one.

## Open questions
- No open copy of ISO 13850, IEC 60204-1, ISO 3691-4, ANSI/RIA R15.08, ISO 18497 or ISO 13855 was found. The ISO 13855 formula and the AGV stopping-distance method are now cited through SICK's manual [C3-S46], and R15.08's scope through [C3-S45], but exact clause text (speed-monitoring requirements, reset rules) is still not citable.
- No source gave a measured end-to-end latency budget from a navigation controller to wheel motion for a mobile robot (Puck et al., CASE 2021 — **not downloaded**, IEEE only).
- When an inner heading-hold or yaw-rate loop in the base driver is acceptable beneath a navigation controller that closes the same state is answered only indirectly: PX4 shows a designed cascade with a yaw-rate loop at the bottom [C3-S41], and cascade theory gives the separation rule [C3-S03]. No source analyses a heading-hold loop placed after a slew limiter under a predictive controller.
- No primary source was found for "zero-velocity hold" in velocity-controlled robot bases (holding position under load at zero command) other than the SOS drive function definition [C3-S09, Table 5.2] and the brake idle mode of motor controllers [C3-S48].
- Agricultural machine standards (ISO 18497, ISO 25119) were not covered by an open source. ISO 26262 appears only through one fail-operational concept paper [C3-S53]; no open ISO 26262 overview was used.
- Tang et al. (RTSS 2020) and Blaß et al. (RTSS 2021) are cited only through the survey [C3-S50]; no open copies found.
- No source describes fault-injection tests of a command multiplexer (killing a publisher, stale stamps, lock toggling) with pass criteria.
- The Cervin et al. *IEEE Control Systems Magazine* (2003) paper on control timing was not found as an open copy; the thesis [C3-S42] was used instead.
